# Load test, 2026-11-19 (T-116)

Script: `tests/load/smoke.js` (k6 2.3.0), unchanged from the [2026-11-16 smoke](2026-11-16-smoke.md):
- 50 trading VUs, one account each: an NVDA proposal, five assessments, then the same order twice at once with one Idempotency-Key.
- 50 readers on `/portfolio`, `/signals` and `/portfolio/positions` for 60 s.

Environment:
- **Stack:** the isolated load stack (`infra/docker/docker-compose.load.yml`: its own project, database and ports, fake market) on Docker Desktop (macOS, Apple Silicon).
- **Also running on the machine:** the everyday stack on real Alpaca data, Ollama, Metro and the iOS simulator.
- **Rate:** about 10 iterations/s.

## What changed since 2026-11-16

Profiling the reads with SQL logging on (`SQL_LOG_LEVEL=Information`) showed two avoidable costs:
- **Trading calendar:** the calendar row for today was read about 11 times per request. `MarketClock` now caches stored rows for 10 minutes.
- **Signals list sparklines:** each row loaded its sparkline through the full daily-history path (instrument, bars, corporate actions, quote, calendar and gap check). `IPriceHistoryProvider.GetTrailsAsync` now loads a whole page's sparklines in one query, with the same split adjustment.
- **Result:** the signals list went from 22 queries to 8 for a single signal, and the per-row cost is gone. A warm portfolio read takes 6 queries and about 20 ms.

## Results

| Measure | Target | 2026-11-16 (B) | Run 1 (cold start) | Run 2 |
|---|---|---|---|---|
| Orders p95 (NFR-02) | ≤ 500 ms | 406 ms | 535 ms ✗ | **230 ms** ✓ |
| Reads p95 (NFR-01) | ≤ 300 ms | 382 ms ✗ | 157 ms ✓ | **77 ms** ✓ |
| Assessments p95 (held to NFR-01) | ≤ 300 ms | 481 ms ✗ | 265 ms ✓ | **149 ms** ✓ |
| Duplicate fills | 0 | 0 | 0 ✓ | **0** ✓ (50/50 accounts: one position, one fill of cash) |
| Checks | 100 % | 100 % | 100 % | **100 %** |

Run 1 started seconds after the stack booted, so its order p95 includes first-call JIT and connection-pool warm-up. Run 2 is the steady state.

## Verdict

NFR-01 and NFR-02 are met with headroom on a developer laptop running two stacks. The duplicate-fill guarantee holds under concurrent identical submits. T-116 is done. A staging run is part of T-117.
